# LBK Launcher

Electron 44 + React 19 desktop app (Windows, macOS, Linux incl. Steam Deck) that installs Ukrainian game localizations. Catalog lives in a local better-sqlite3 DB synced from Supabase; the installer downloads and extracts archives into detected game folders and wires up Steam integration. UI copy is Ukrainian, code identifiers are English. `package.json` version is currently 2.24.0.

## Commands

```bash
pnpm dev              # prebuild (bridge + spellfix) + electron-vite dev, renderer on port 5173
pnpm build            # electron-vite build → out/{main,preload,renderer}
pnpm prebuild         # pnpm build:bridge && node scripts/build-spellfix.js
pnpm type-check       # tsc --noEmit, then tsc -p for each packages/lbk-bridge-* — CI gate 1
pnpm test:unit        # pretest:unit builds the bridge, then vitest run — CI gate 2
pnpm lint             # eslint . — CI gate 3
pnpm format:check     # biome check --max-diagnostics=200 . — CI gate 4
pnpm find-unused      # knip — CI gate 5, an unused export fails the build
pnpm format           # biome check --write .
pnpm dist:win|linux|mac        # electron-builder → release/<version>/
pnpm dist:mac:local            # env-cmd + CSC_IDENTITY_AUTO_DISCOVERY=false
pnpm test:e2e         # playwright over CDP :19222 against the packaged app
pnpm build:bridge     # wireit: build packages/* (CDP ops and achievement page IIFEs, Millennium ttc index.js/webkit.js, Decky rollup) only when their inputs changed; gitignored output, fingerprints and cache in .wireit/
pnpm dev:bridge       # the same builds in watch mode; `pnpm dev` does not watch packages/
```

Each package's `wireit` block in its `package.json` lists the inputs (`files`, the lockfile, the workspace packages it reads) and `output`; a build input missing there leaves a stale bundle after `pnpm dev` / `pnpm test:unit`, so add it when a build starts reading a new file. `.github/workflows/ci.yml` runs `pnpm build:bridge` after install (the `?raw` ops import, tests and knip need the output), then gates 1–5 in that order on Node 24.22.1 / pnpm 11.4.0. `--publish never` is not in the scripts — `release.yml` appends it to `pnpm dist:*`. `.husky/pre-commit` runs `npx lint-staged`, which runs only `biome check --write --no-errors-on-unmatched` on staged `*.{js,ts,tsx,json,css,scss}`; type-check, eslint and knip do not run locally.

## Architecture

Three processes plus a DB worker thread. `electron.vite.config.ts` builds **two** main-process rollup entries: `index` (`src/main/index.ts`) and `db-worker` (`src/main/db/db-worker.ts`). `better-sqlite3` and `electron-liquid-glass` are rollup externals; the ESM-only `got`, `electron-store`, `fast-vdf`, `resedit`, `p-timeout`, `p-memoize`, `p-limit` and `p-wait-for` are deliberately bundled (`externalizeDeps.exclude`) — the main build is CJS, and externalized they arrive through `require(esm)` as a namespace, so a default import hits rollup's interop (`got.stream is not a function`, `ElectronStore is not a constructor`) on first use, at runtime only. `binarykvparser` is bundled too: it ships `long` as a bundledDependency, which electron-builder drops from `app.asar` (the packaged app crashed on start). `bundled-dependencies.test.ts` fails for any dependency that ships bundledDependencies, and for any ESM-only one (no `require` condition on its root export) missing from a build's own `exclude`: the main build's for what `src/main`, `src/shared`, `src/lib` or `packages/lbk-bridge-core/src` imports, the `preload:` block's (none today, so it externalizes every dependency) for what `src/preload/index.ts` reaches through relative and `@/` value imports.

**Only `@` is aliased in the main and preload builds.** `@renderer`, `@components`, `@store` and `@resources` exist solely in the renderer build even though `tsconfig.json` declares all five, and vite does not read tsconfig paths — a value import through one of them from main/preload passes `pnpm type-check` and then fails at build. Use `@/...` outside the renderer.

The whole app body lives inside the single-instance-lock `else` branch of `src/main/index.ts` (`if (!gotTheLock) { app.quit() } else { … }`). Put new app wiring inside it, or it runs in the doomed second instance too.

### IPC — six bridges, not one

`src/preload/index.ts` calls `contextBridge.exposeInMainWorld` six times: `electronAPI`, `windowControls`, `liquidGlassAPI`, `loggerAPI`, `api`, `storeStorage`.

- `electronAPI` is typed by the `ElectronAPI` interface in `src/shared/types.ts` (`const electronAPI: ElectronAPI = {...}` makes a missing method a compile error), and `declare global` there adds it to `Window`. The Millennium / Decky / Steam-bridge payload types (`PluginHostState`, `SteamBridgeStatus`, `MillenniumInstallResult`, `RestartSteamResult`, …) live in `src/shared/plugin-host-types.ts`, together with `SteamPluginHostAPI`, the Steam-bridge and Millennium / Decky methods that `ElectronAPI` extends; import them from there, and add a method of that group to `SteamPluginHostAPI`, not to `ElectronAPI`. The reviews and feedback methods are the same kind of group: `GameReviewsAPI` (with its inputs, `ReviewResult` and `ReviewFailure`) in `src/shared/game-reviews-api-types.ts`, wired from `src/preload/game-reviews-api.ts`, which `src/preload/index.ts` spreads into `electronAPI`.
- The other five are typed by hand in `src/window.d.ts`, except `windowControls`' notification methods (`showSystemNotification`, `onNavigateToGame`): those are `SystemNotificationAPI` in `src/shared/game-link-target.ts`, implemented by `src/preload/system-notification-api.ts` (spread into `windowControls`) and merged into `window.d.ts`'s `WindowControlsAPI` by that file's `declare global`, so add a notification method there, as with `SteamPluginHostAPI`. Editing `src/shared/types.ts` for them does nothing.
- `src/env.d.ts` owns `ImportMetaEnv` (the `VITE_*` keys) and `declare const __SENTRY_RELEASE__`. It is incomplete: `VITE_SENTRY_DSN` is read in `src/main/index.ts` and listed in `.env.example` but is missing from the interface.

To add a channel (data main keeps current for the page is a resource instead, see below):
1. Register inside the matching setup function in `src/main/ipc/` — `games.ts`, `installer.ts`, `likes.ts`, `links.ts` (`open-app-link`: a Telegram, Discord, Steam or Epic Games Store web link opened in its app, Steam through the Millennium launch path, Epic's `/p/<slug>` pages as `com.epicgames.launcher://store/p/<slug>` (the launcher's `store/product/` route opens only the store's front page), with the link itself as the fallback; per-app mapping in `src/main/utils/app-links.ts`, fallback in `openWithFallback()` in `src/main/utils/open-external.ts`), `tg-news.ts`, `game-reviews.ts` (`reviews:*`, inputs passed through as typed, like every other channel from our own renderer; `reviews:sync-events` replays missed review events), `plugin-host.ts` (`plugin-host:*`, `millennium:*`, `decky:*` and the Steam bridge channels `restart-steam`, `get-steam-bridge-status`, `recheck-steam-bridge`, `set-steam-cef-debugging`), `window-controls.ts` (that one exports `setupWindowControls`, not `…Handlers`, and is a grab-bag: `show-system-notification`, `clear-cache-only`, `clear-all-data-and-restart`, `logger:log` and `logger:open-logs-folder` live there too — look there before adding a logging, cache-clearing or notification channel; main-process code shows a notification through `showSystemNotification()` in `src/main/utils/system-notification.ts`). Handlers also live outside `ipc/`: `src/main/window.ts` (`liquid-glass:*`, registered at module import time), `src/main/utils/store-storage.ts`, `src/main/auto-updater.ts`, `src/main/changelog.ts`, `src/main/sync-status.ts` (`get-sync-status`; `setSyncStatus()` pushes `sync-status` and emits it on `appEvents`, `isCatalogReady()` is `ready` or `error`), `src/main/index.ts`. Register a handler with `handleOr(channel, run, fallback)` from `createHandleOr('<Tag>')` (`src/main/ipc/handle-or.ts`, `{ timed: true }` adds a `createTimer`): a throw is logged as `[<Tag>] <channel> failed:` and answered with the fallback (`orNull`, `orEmpty`, `orFailure` for `{ success: false, error }`, or the file's own), so a handler body never needs its own try/catch.
2. Call the setup function from `src/main/index.ts`, next to the other `setup*Handlers()` calls. Nothing is auto-discovered.
3. Add the method to `ElectronAPI` in `src/shared/types.ts` (or its group interface), **or** to `src/window.d.ts` for the other five bridges (a `windowControls` notification method to `SystemNotificationAPI` instead).
4. Wire it in `src/preload/index.ts`, or in the module it spreads for that group (`game-reviews-api.ts`, `system-notification-api.ts`), with the builders of `src/preload/ipc.ts`: `invoke(channel)`, `send(channel)`, `listen(channel)`, which take their argument and result types from the interface member they are assigned to, so the preload holds no hand-written wrappers. Write a method by hand only when it reshapes its arguments (`setGameVisibility`), is synchronous (`sendSync`) or transfers a `MessagePort` (`connectResources` in `resources-api.ts`).

**Push-event bridges own their teardown.** All 22 `on*` methods of the main window's preload (`src/preload/index.ts`, `game-reviews-api.ts`, `system-notification-api.ts`) are `listen(channel)`, which returns `() => ipcRenderer.removeListener(channel, handler)`, typed `(cb) => () => void` in `ElectronAPI` / `window.d.ts`; call it from effect cleanup — dropping it leaks a listener on every remount, and `removeAllListeners` would kill other subscribers of the same channel.

**Data main keeps current for the page is a resource, not a channel and a bridge per list.** `ResourceMap` in `src/shared/resources.ts` names each one (`facetRows`, `catalogOptions`, `libraries`, `installedTranslationIds`, `ratings`, `storeDiscounts`, `likedGameIds`, `homeInstalled`, `weeklyPicks`, `popularGames`, `newStarGames`, `steamBridgeStatus`, `pluginHostState`, `wineBottles`). `DEFINITIONS` in `src/main/resources/start-resources.ts` gives each a `read` and the `appEvents` names that make it stale, plus `afterCatalogSync` for reads of the catalog, which wait for `isCatalogReady()` and re-read at once on `sync-status` (the sync writes through the worker and emits no per-game events). Every source is an `appEvents` event, renderer settings included: `setupStoreStorageHandlers()` (`src/main/utils/store-storage.ts`) emits `hide-ai-changed` when a settings write changes `hideAiTranslations` (the renderer rewrites its whole envelope on any change) and `workshop-installs-changed` on every write that changes the Workshop installs (electron-store's `onDidChange` skips an equal value). `defineResource()` returns a `Resource` handle whose `wanted()` the port calls for each key a subscribe names (`startResources()` builds the `Record<ResourceKey, Resource>`); the first call starts the key (`F.once`) and from then on it stays current for the rest of the run, page or no page: every call reads at once (a new page reads every key again, and a view's `refreshResource()` is the same subscribe; an unchanged value sends nothing) and 300 ms after the last of a burst of events (`F.debounce`; `hide-ai-changed`, which a toggle sends alone, at once: `UNBATCHED_EVENTS`), one read at a time (`p-limit(1)`) with at most one more waiting (`pendingCount`); a read that has not settled after 30 s (`p-timeout`) is abandoned, not stopped, so the next one may start beside it, and its late value is dropped. A read that times out, throws or rejects (an `AbortError` included) logs `[Resources] Failed to read`, marks the key failed, keeps the last value and is read again on the next event or subscribe. `publishResource()` (`resource-hub.ts`) drops a value deep-equal to the last one, unless the key was failed: then the equal value goes out to clear it. Owners may publish at any time, before any subscribe too. A definition with `withCounters` (`homeInstalled`, `weeklyPicks`) lays the rows of each `counters-changed` over the value it holds instead of reading again (`patchResource()`: nothing goes out when no held game changed, and a failed key stays failed); a patch that throws logs `[Resources] Failed to patch` and reads the key in full instead, so the throw never reaches the counters feed or the other listeners. Nine resources follow `catalog-changed` and `sync-status` alike, which is why `appEvents.setMaxListeners(50)`. The owners of the two Steam values publish each one they compute (`getSteamBridgeStatus()`, `getPluginHostState()`); `pluginHostState` is also re-read on `steam-started` / `steam-exited`, which its owner does not republish for. Everything travels over one `MessagePort`: the preload's `connectResources()` (`src/preload/resources-api.ts`) makes a `MessageChannel`, sends main one end as `resources:connect` (`resource-port.ts`, which takes it only from the main window) and hands the page the other with `window.postMessage` (a `contextBridge` function cannot carry a port), and structured clone keeps `Map` and `Set`. A new page's connect closes the old session's port and gets one snapshot of every value and failed key main holds; every later value goes to that page, subscribed to its key or not. Each message (`ResourceUpdate`) carries what changed and every failed key, so the renderer replaces its failed set; a port that cannot take a message logs `[Resources] Failed to publish` and throws into nothing. The subscribe message is passed through as typed, like every other channel from our own renderer. In the renderer `initResources()` (`store/resourcesBridge.ts`, once from `main.tsx`) subscribes each key as `SUBSCRIBE_AT` says (`satisfies Record<ResourceKey, 'start' | 'idle'>`, so a key cannot be left out): the home page's and the game list's at once, the filters', `ratings` and the two Steam ones on idle, so their reads stay out of the first render; `useResourcesStore` holds the values and the failed keys, and components read `useResource(key)`: a `Resource<T>` (`utils/resourceOf.ts`) that is `loading`, `ready` with the value, or `failed` for a first read that failed with nothing to show (a failure after a value keeps it `ready`); `useRefreshedResource(key, enabled)` also asks main to read the key again each time `enabled` turns on. A new resource is a `ResourceMap` key, a `DEFINITIONS` entry, a `SUBSCRIBE_AT` entry and an `appEvents.emit` where its source changes: no channel, preload method or store. Its source events are main-only (`catalog-changed`, `library-changed`, `installs-changed`, `counters-changed`, `likes-changed`, `store-discounts-changed`, `weekly-picks-changed`, `hide-ai-changed`, `workshop-installs-changed`, `wine-prefixes-changed`); `notifyCountersUpdated()` (`src/main/db/counters-updated.ts`) sends `game-counters-updated` to the list and emits `counters-changed` with the same rows in one call.

**Handlers never throw across the boundary.** Return `{ success, error }` — custom Error properties do not survive IPC. `src/main/ipc/installer.ts` maps `ManualSelectionError` / `RateLimitError` / `NetworkError` (all from `src/main/installer/errors.ts`) into `needsManualSelection` / `isRateLimit` / `isNetworkError` booleans. Read-only handlers return `null`/`[]` instead. The `reviews:*` channels return `ReviewResult` (`{ ok: true, data }` or `{ ok: false, failure: { code, kind } }`) instead, and the renderer reaches them only through `src/renderer/queries/reviewsClient.ts`.

Window channels are colon-separated: `window:minimize` (which **hides to tray** — the tray is the only way back), `window:maximize`, `window:close`, `window:is-visible`. Maximize state is pushed as the `window:maximized` event from `src/main/window.ts`; there is no `window-is-maximized` handler.

## Database and sync

`src/main/db/database.ts` is a synchronous better-sqlite3 singleton on the main thread. Get the handle with `getDatabase()` — `DatabaseManager` is not exported and has no `.prepare`.

- **The worker thread does WRITES ONLY**: `upsertGames`, `deleteGame`, `deleteGames`, consumed solely by `src/main/db/sync-manager.ts`. Every read, FTS5 search and spellfix fallback runs synchronously on the main thread: `GamesRepository`, plus `deep-link-game.ts` (`findDeepLinkGameId`) and `recommendations-source.ts`.
- `src/main/db/db-worker-client.ts` resolves the worker at `process.resourcesPath/app.asar/out/main/db-worker.js` when packaged. Nothing type-checks that string — renaming the rollup entry breaks sync at runtime only.
- **Migrations are name-keyed, not versioned.** `src/main/db/migrations.ts` replays the entire array on every start with no `user_version` and no applied-migrations table. Every migration must self-check: column adds via `addColumnIfMissing()`, one-shot data work via a marker row in `sync_metadata` (`forceResyncOnce()`). `runMigrations()` rethrows, so a throw propagates out of the `DatabaseManager` constructor.
- **Migrations never run on a fresh DB.** `database.ts` calls `createTables()` and returns; `runMigrations()` is only reached for a pre-existing DB that already has a `games` table. Anything that must also hold for first launch has to be duplicated into `createTables()`.
- **Adding a `games` column is a five-place lockstep change**: the DDL in `createTables()`, an `addColumnIfMissing` migration, `gameToInsertParams()`, the `SYNCED_COLUMNS` array (both in `src/main/db/db-queries.ts`), and usually a `forceResyncOnce` migration. The `_assertNever<…>()` guards in `db-queries.ts` make `pnpm type-check` fail if steps 3/4 diverge; steps 1/2/5 fail silently at runtime.
- `UPSERT_GAME_SQL` uses `ON CONFLICT(id) DO UPDATE` built from `SYNCED_COLUMNS` specifically so `user_unlocked` (local-only, how a user reveals a `hide = 1` translation) survives sync. Any new local-only column must stay out of `SYNCED_COLUMNS`; never switch to `INSERT OR REPLACE`. The counters (`likes`, `downloads`, `subscriptions`, `reviews`, `error_reviews`) are written on insert but skipped on conflict (`COUNTER_COLUMNS`): after insert only `src/main/db/game-counters.ts` updates them (`get_game_counters` rows, `game-counters` broadcasts of `[id, likes, downloads, subscriptions, reviews, error_reviews]` tuples, read with `.rest()`, so an element the server appends later never drops a broadcast), so a games page fetched before a counters broadcast cannot roll them back. A new counter column therefore needs no resync: its migration deletes `game_counters_synced_at` instead (`add_review_counter_columns`), so the next catch-up refetches every game's counters.
- **Every query that lists games must use `VISIBLE_GAMES_SQL`** (`db-queries.ts`) or it leaks hidden translations. It is `approved = 1 AND (hide = 0 OR user_unlocked = 1)`, relaxing to `approved = 1` when `IS_ADMIN_BUILD` (`src/shared/admin-mode.ts`, from `VITE_ADMIN_MODE`, set only by `.github/workflows/tg-build.yml`).
- Search (`src/main/db/search-condition.ts`): FTS5 for ≥ 2 chars, first with the query's numbers and then without (`buildFtsQueries()`), `name_search LIKE ?` lowercased in JS for 1 char (SQLite's LIKE folds ASCII only; every LIKE escapes the query's `%`, `_` and `\` with `ESCAPE '\'`, or `%` lists the whole catalog), `name LIKE ?` when tokenization yields nothing, then the same for the query in the other keyboard layout (`switchLayout()` via `convert-layout`, `цфк` → `war`, not transliterated again). Only when that finds no visible game and `isSpellfixAvailable()` does the spellfix fallback run: words that find a game stay as typed, the rest take the first candidate (`distance <= 100` or an adjacent swap) that still finds a game with the other words, all ANDed, and 3+ words that still find nothing get the leave-one-out ORs. A game missing from the catalog must return 0 rows, or `trackFailedSearch` never sees it. With the default name sort a search listing puts manual translations (`ai IS NULL`) first, then within each kind titles that start with the query (`prefixFirstOrder()`), then the translation rating; any other sort keeps only the prefix rule before it. The prefix rule takes the query in the forms the match read it: the other layout, the transliteration or the spellfix correction when that was what matched, both sides without apostrophes (`SearchCondition.prefixes`). The dictionary table is `spellfix_words` (a flat list of the ≥3-char words of `name`, no transliterated forms) and is fully rebuilt on every batch upsert. `games_fts` is `fts5(game_id UNINDEXED, name_search, search_keywords, tokenize='unicode61')`, maintained by manual delete+insert. Cross-script matching (Cyrillic query → Latin title and back) comes from transliteration, not spellfix: `generateSearchableString()` in `src/shared/search-utils.ts` stores lowercased `name` plus its `cyrillic-to-translit-js` transliteration plus an apostrophe-stripped variant into the derived `name_search` column at upsert time, and `buildFtsQuery()` transliterates the query the same way. `name_search` is written, never computed at read time — changing the search helpers needs a reindex migration over existing rows (see `reindex_fts_without_apostrophes`), not just a redeploy.
- `SyncManager.getInstance().sync(...)` does a full sync when the games table is empty or no `last_sync_timestamp` exists, otherwise a delta, falling back to full on delta failure. There is no staleness window.
- **Sync is cursor-based end to end.** Each cursor is the server's own newest timestamp among the rows received, never the local clock: `last_sync_timestamp` (games `updated_at`), `deleted_games_synced_at` (`deleted_at`), `tag_names_synced_at`, `game_counters_synced_at` and `store_discounts_synced_at` (`touched_at`). Games and deletions are read rewound one minute (`rewind()` in `src/main/db/sync-cursor.ts`) to catch rows committed late, which is safe because every apply is idempotent; tag names are not, since one bulk write gives them all the same timestamp. Pages are keyset, never `.range()` offsets: order by the cursor column plus a unique tie-breaker and continue with `afterCursor()`, since an offset shifts when rows change mid-run and silently skips one.
- **A new delta + realtime feed goes through `createDeltaStream()`** (`src/main/db/delta-stream.ts`): `fetchSince` yields batches and the watermark is saved only on batches that carry one, broadcasts are zod-checked, a catch-up asked for during a pass queues another after it (`pLimit(1)`), and every realtime join catches up, the first one included (`onSubscribed`), so nothing broadcast between a startup catch-up and the join is missed. `game-counters.ts`, `review-events.ts`, `store-discounts.ts` and `weekly-picks.ts` are the four users. Every topic only the server broadcasts on is `private: true` (`games-broadcast`, `game-counters`, `store-discounts`, `home-picks`; lbk-admin migrations 206 and 207): `realtime.messages` policies let clients receive them, and with no INSERT policy nobody holding the anon key can send on them. Only the per-machine `feedback-replies:machine:<id>` topic is still public.
- **Review events** (`src/main/review-events.ts`) are the one subscription on `feedback-replies:machine:<machineId>`: it listens to `review` only (the topic's legacy `INSERT` is for shipped launchers), and its catch-up is `get-feedback-replies` with `version: 2` through `callReviewFunction()`. Each item is zod-checked alone (`keepValid()`, `src/main/db/keep-valid.ts`). The watermark `review_events_synced_at` is the last kept event's `at` as sent, never parsed into a `Date` (it has microseconds); live events never move it. A machine without one seeds it once from the replaced stream's `last_feedback_reply_sync` and catches up from there, or else from the local clock with no catch-up, so history is never backfilled; a failed or unreachable catch-up neither moves it nor throws. A page of 200 or more (`WITH TIES` never splits one `at`) pages on from its last raw item's `at`, parsed alone, so a page whose every event is dropped still pages on. The first page of each catch-up starts 5 s early, so events committed late are not lost. Main sends each catch-up page, or a live event alone, as one `review-events` message to the main window and keeps no dedupe of its own: the renderer's seen lists drop repeats (below). Delivery is on only while a page listens: the bridge's `reviews:sync-events` (`syncReviewEvents()`) turns it on once its listener is set, and `src/main/window.ts` turns it off (`stopReviewEvents()`) on a main-frame cross-document `did-start-navigation`, on `render-process-gone` and on `closed`. While it is off, live events go nowhere and a catch-up asks nothing (one in flight stops after its page), so on macOS a closed window or a reloading page never lets the watermark pass events nobody received; the new page's own `syncReviewEvents()` replays them.
- **Every call to the `reviews` and `submit-feedback` edge functions (and the review events catch-up of `get-feedback-replies`) goes through `callReviewFunction()`** (`src/main/db/review-request.ts`): the reads in `READS` (`list`, `author`, the catch-up) time out after 15 s, and every other call is a write, which times out after 30 s and refuses in E2E. Main appends the machine id, when it has one, after the caller's fields (the renderer never sends one). A 2xx body gets one `safeParse` with the caller's schema: the response schemas live in `src/shared/game-reviews-types.ts` and `src/shared/game-reviews-api-types.ts` with their types as `z.infer`, and the renderer imports only the types. Every failure is classified once in `src/main/db/review-failure.ts` into a server or local code and a `kind` (`retry`, `needs-author`, `rejected`); only `retry` may be resent as it is, since a nickname cannot come from a resend. A non-2xx body is read for 5 s at most (`readFunctionsErrorBody()`; functions-js has already cleared its timeout), a 4xx with no known code is final: `refused` (a warning) when its envelope names a code newer than the build, `gateway_refused` (a Sentry error: a missing function or a bad key) when the gateway answered other than 429 and 408 with no envelope, and `bad_response` is kept for a 2xx that breaks the schema. A public write passes a token source as the last argument (`() => takeCaptchaToken(action)`), asked once per call; `captcha_failed` is a `retry` kind, so the player's resend takes a fresh token. Which writes need one: a `submit-feedback` with `allowPublish`, a reply or edit whose renderer-sent `isPublic` hint says the thread is public, and every `claim`. When no token can be had, the write still goes out without one, so a resend of a stored post or entry is answered before the captcha check and the server's `REVIEWS_CAPTCHA=off` switch (meant for a Turnstile outage) can pass it. A bad 2xx body is logged with `z.prettifyError()` (paths and expectations, never values) as a `console.error`, so a contract break reaches Sentry. The list is parsed whole: one malformed thread, reply or focus thread fails the page as `bad_response`, so a server enum value a shipped launcher does not know must not reach it; the list request carries `version` (`app.getVersion()`) so the server can tell.
- **Turnstile tokens come from a hidden window in main** (`src/main/turnstile/`): `window.ts` loads `VITE_CAPTCHA_PAGE_URL` (no default; missing or not https → no token) lazily on the first token need, in a sandboxed window on its own in-memory session (`session.ts`, every permission denied, every download cancelled) and no preload; once the page has loaded, each token is one `webContents.executeJavaScript('window.lbkCaptcha.solve(action, cData)')` (the landing page script's whole contract), whose `{ token }` or `{ error }` is zod-checked and raced against the window going. The window is destroyed with the main window (or `window-all-closed` never fires on Windows/Linux), on `before-quit` and after 3 min idle. Landing faults that stop every public write (the missing URL, a non-200 page, a solve that throws or answers malformed or `script_error` (each closes the window, so the next token reloads it), any widget error, no token in 30 s; a slow page is never closed for it and serves the next request) are logged by `reportCaptchaFault()` (`report-captcha-fault.ts`) as a `console.error`, a Sentry event, once per cause and run, and as a warning after; a failed load (the user's network) and a crashed renderer stay warnings. `tokens.ts` binds each token to its action and `cData` (`sha256(machineId)`, first 32 hex), keeps one prefetched token per action for at most 240 s (`reviews:prefetch-captcha`, `usePrefetchCaptcha()` in the composer) and hands it to one write only. The token never reaches the renderer, and E2E never opens the window. Never override the User-Agent: the landing serves the page only to one with `Electron/`, and Turnstile wants it unchanged.
- **Likes**: `src/main/likes.ts` owns `my_likes(game_id, liked, server_liked)`. A row with `liked != server_liked` is unsent. The shown count is the server count plus that unsent toggle (`likesWithUnsentSql()`, also used by `game-counters.ts`). Clicks are debounced per game (400 ms) and sent one at a time through the `track` edge function. A toggle folded back to `server_liked` is never sent. 4xx reverts to `server_liked`, network/5xx retries after 60 s. `syncLikes()` on startup takes the server's `liked_games` list, except for unsent rows. Every change emits `likes-changed` (the `likedGameIds` resource) and goes through `notifyCountersUpdated()` for the count. `initLikes()` (`src/renderer/store/likesBridge.ts`, once in `main.tsx` after `initResources()`, outside React; store bridges go there, not into hooks in `App.tsx`) copies that resource into `useLikesStore`, which flips a click at once and keeps the clicks main has not answered (`pendingClicks`), so a resource value read before a later click does not undo it; the `likes:set` reply (main's liked set) settles each click, a no-op or failed one included, since an unchanged set sends no resource value.
- **Store discounts**: `src/main/db/store-discounts.ts` keeps only active discounts in `store_discounts(store, steam_app_id, discount_percent, ends_at epoch ms | NULL)`, `store` being `steam`, `gog` or `egs`, from `get_store_discounts` (pages of 1000 by `(store, steam_app_id)`) and `store-discounts` broadcasts of `[store, steam_app_id, percent, ends_at seconds | null]` tuples; a catch-up page skips the keys a broadcast wrote since that catch-up began (it may have been read before them), a store this build does not know is left out, a row with percent 0 or a passed end deletes, a GOG row has no end and stays until a broadcast ends it, and `store-discounts-changed` goes out on `appEvents` only when a row changed. The `storeDiscounts` resource (`getStoreDiscountsByApp()` in `src/main/store-discounts-by-app.ts`: a `Map` per app id, the biggest first) leaves out games in the player's library of that store (Steam by app id, GOG and Epic by title through `findGamesByTitles`, as the library filters match them) and is re-read on `store-discounts-changed`, `library-changed`, `catalog-changed` and `sync-status`; it does not wait for the sync, since the table and last run's catalog are already there; components read it through `useStoreDiscounts(steamAppId)`, and `DISCOUNT_STORES` (`src/renderer/components/Elements/discountStores.ts`) gives each store its name, icon, page and opener: the list pill shows the biggest discount, the hero a `StoreSaleButton` per store whose page the translation has. GOG opens in the browser, since no GOG Galaxy link to a store page is verified. An ended discount goes when the admin `prices` job (18:05 UTC, after Steam's 17:00/18:00 UTC ends) broadcasts it, with no renderer timer.
- **Weekly picks**: `src/main/db/weekly-picks.ts` keeps the one current set in `weekly_picks(id = 1, title, starts_at epoch ms, game_ids JSON in the set's order)`, from `get_home_picks` on every catch-up (the whole state, so no watermark) and the private `home-picks` broadcast (event `set`, the same row) that lbk-admin's migration 206 sends when a new set commits; a set older than the stored one is ignored, and `weekly-picks-changed` goes out on `appEvents` only when the row changed. The `weeklyPicks` resource (`getWeeklyPicks(hideAi)`) reads the games from the local catalog in the set's order, so a hidden, unapproved or AI-filtered game is left out without a new set; it is re-read on `weekly-picks-changed`, `catalog-changed` and the AI toggle. `WeeklyPicksSection` shows a loader until the first value, nothing without a set (`null`) or when that first read failed, and a later failed read keeps what is shown (`useResource('weeklyPicks').status`). The counters feed's rows are laid over the held set without a read (`withCounters` with `withUpdatedGames()`, `src/main/resources/with-updated-games.ts`), as for `homeInstalled`, whose read would rescan every store library.
- **Translation rating** lives only in SQL: `TRANSLATION_RATING_SQL` in `src/main/db/translation-rating-sql.ts` (0.45 × the like rate smoothed toward 10 % over 70 downloads, 0.25 × quality: manual 1, `edited` 0.8, other AI 0.55, 0.2 × log10 of downloads and 0.1 × log10 of `reviews`, each plus one, negative or null counters as 0), with no JS copy; lbk-admin's `translation_rating()` (migration 211, behind `games_grouped` and `fuzzy_search_games`, and `get_game_translations()` of migration 212, which gives the landing a game's translations in rank order) mirrors it, so change both together. `TRANSLATION_RANK_SQL` (manual first, then the rating, then `translation_progress`) orders a game's translations: every catalog list of `GamesRepository` goes through `catalogSelectSql()` (`catalog-select.ts`), which keeps the requested order for the games and lists each game's translations (`getGameGroupKey()` in SQL) together where its first one falls, best first, so the sidebar groups and the home installed card (`translations[0]`) only keep the SQL order; `GetGamesParams.flat` turns the grouping off for the home page's newest and updated lists. Rows patched in place (counters feed, realtime, `withCounters`) keep their place until the next read. `popularGames` is every translation with 70+ downloads and `newStarGames` those added (`created_at`) in the last 21 days with fewer, not `planned`, both by rating, 30 at most (`ranked-home-games.ts`); they are re-read on `counters-changed`, so a translation moves from one to the other with its 70th download, and leaves «Нові зірочки» on its 21st day only at the next read.
- Server-side deletions of games whose translation is still installed are **tombstoned** into `pending_game_deletions` in `sync_metadata` and cleared later by `processPendingDeletions()`.
- Realtime is broadcast-channel based (`src/main/db/supabase-realtime.ts`), not `postgres_changes`; `subscribe()` takes an **array** of `BroadcastSubscription` objects.
- **Clearing the catalog DB is two-phase and restart-based**: `clear-cache-only` / `clear-all-data-and-restart` call `closeDatabase()` → `deleteDatabaseFile()` → `app.relaunch()`. `deleteDatabaseFile()` unlinks `lbk.db`/`-wal`/`-shm` eagerly and, if an unlink fails (Windows keeps WAL files locked), writes a `lbk.db.delete` marker in userData that the `DatabaseManager` constructor consumes on the next launch. Never unlink the DB files directly — go through `deleteDatabaseFile()`.

## Installer

Orchestrator is `src/main/installer.ts` (there is no `src/main/installer/index.ts`). Order: platform compatibility → resolve gamePath (custom paths blocked for `license_only`) → `resolveGameBuildOs()` → stage into `<gamePath>/.lbk-temp` → disk check for 2× archive size → download+extract → optional backup → copy → cleanup → `saveInstallationInfo` → `applySteamIntegration`.

- **Archive variant priority**, identical in the disk-space step and the download step and must stay in sync: build-OS variant (`steam_linux_*` / `steam_mac_*`) → store-specific (`epic/gog/xbox/uplay/ea_*`) → `archive_path`. `resolveGameBuildOs` (`src/main/utils/game-build.ts`) sniffs ELF/Mach-O magic on disk, then Steam's compat tool, then host OS — the host OS is *not* the build OS for Linux Steam titles under Proton.
- **There is no macOS installer column** — only `installation_file_windows_path` and `installation_file_linux_path` exist. macOS falls back to the Linux path and runs it directly after `chmod +x`; `checkPlatformCompatibility()` (`src/main/installer/platform.ts`) blocks a translation on macOS when only the Windows installer exists.
- Install metadata is written **twice**: `.lbk-translation.json` in the game folder and a mirror at `userData/installation-cache/<gameId>.json`. The userData directory is the source of truth for "what is installed" (`getAllInstalledGameIds()` reads filenames). `src/main/installation-watcher.ts` fs.watches it with a 100 ms debounce; `checkInstallation()` rewrites the cache only when fields actually changed, to avoid a watcher feedback loop. The record's `steamArtwork` is the player's last artwork choice for that game, written only by an install dialog that offered artwork (`withSteamArtworkChoice()`) and by the artwork-only change; a reinstall dialog starts its artwork box from it, and without it from the artwork on disk or the setting (`steamArtworkStartsChecked()`). Artwork is offered only where `offersSteamArtwork()` (`src/shared/offers-steam-artwork.ts`) says so: a Steam install of a game with an app id, an image and `games.artwork_localized`. Main is the gate (`steam-integration.ts`): an install of a game that does not offer it removes artwork applied earlier and leaves the record's choice as it was.
- Backups go into a hidden `.lbk-backup/` dir at the game root and are only written if absent, so re-installing never overwrites the pristine original. Restore tries `.lbk-backup/<rel>`, then legacy `<file>_backup`, then `<file>.kbak`. `findBackupDir()` / `findInstallationInfoFile()` **rename** legacy `.littlebit-*` paths as a side effect.
- Translations shipping an executable installer return early through a `installer:confirm-run` → `installer:run-decision` round trip. The prompt is `initRunInstallerPrompts()` (`store/runInstallerPromptBridge.ts`, called once from `main.tsx`), a mandatory global modal on whatever page is open; mandatory modals queue in `useModalStore` instead of replacing or being replaced, and a `key` lets a prompt re-show itself in place. Main keeps the waiting prompts in `installer/run-decisions.ts` and answers one as skipped (`run: false`, the preselected Proton) when no window can show it, when a newer prompt for the same game comes, and when the page goes (`declinePendingRunInstallers()` at the same three points of `window.ts` as `stopReviewEvents()`), so the install never waits on a page that can no longer answer. That path also returns before the backup/copy branch — it records `installedFiles: []`, `components.text.files: []` and `hasBackup: false`, so no backup exists and uninstall relies entirely on the shipped uninstaller (`installInfo.installerPath`); backup restore is a no-op for installer-based translations and the manual-cleanup fallback has nothing to delete.
- `runProton()` **renames the installer file on disk** to a transliterated name (`renameFileToTranslit`, cyrillic-to-translit-js 'uk' preset) before launching it, so a Cyrillic installer path stored earlier is stale afterwards. `runUninstaller()` and `rerunInstaller()` retry via `getTransliteratedPath(storedPath)` when the recorded path no longer exists — keep that fallback in any new code that re-opens a saved installer path.
- `applySteamIntegration` (`src/main/installer/steam-integration.ts`) is the shared tail for both paths — steps appended after the normal flow were silently skipped for installer-based translations.
- **Achievements never go into `appcache/stats`** — Steam compares the schema's SHA1 with the server and replaces a modified `UserGameStatsSchema_*.bin`. The installer parses the archive's schemas (`prepareAchievements()` in `src/main/achievements/install.ts`; `binarykvparser`, pinned to 2.2.0 because 2.3.0 was published without its bundled `long`; `utils/achievement-strings.ts`) into `userData/achievement-strings/<appid>.json` (`achievements/strings-store.ts`) and records `components.achievements = { files: [], appIds, archiveHash }`; `syncAchievementsToPlugin()` (`src/main/achievements.ts`) aggregates them into the LBK Bridge plugin's `achievements.json` through `writeBridgePluginData()` (Millennium plugin dir and Decky data dir), so translated achievements reach Steam **only through the plugin** (Millennium v3 or Decky). `InstallResult.achievementsDelivery` says which case applies; the install-success modal offers «Перезапустити Steam зараз» only for `plugin-next-start`, and for `plugin-live` while a newer LBK Bridge waits for Steam's next start (`updateAfterRestart`, see Renderer). Re-install is skipped only when `archiveHash` matches **and** this game's strings files exist (`isAchievementsComponentCurrent()`; `hasAchievementStrings([])` is `false`). Records with non-empty `files` are legacy `.bin` copies (v2.0–v2.23.1): at startup `migrateLegacyAchievements()` (`achievements/legacy.ts`) restores each `_backup` or deletes the file and marks the component not installed (`{ installed: false, files: [] }`, both record copies via `rewriteInstallationRecord()` in `installer/installation-info.ts`), so the install dialog offers achievements again — nothing is re-downloaded. The three install endings (achievements only, shipped installer, copied files) share `finishInstall()` in `src/main/installer.ts`; it does not wait for the plugin's reload before saving the record, and waits for its answer, which only the success modal needs, at most 10 s from when it starts waiting (`deliveryWithinInstallWait()`: a reload still queued behind other plugin ops then reads as `plugin-next-start`). Strings go with their record: `'install-record-removed'` on `appEvents` (emitted by `installer/cache.ts`, handled in `startAchievements()`) covers records dropped outside the uninstall flow, and startup removes strings without a record. Both keep the strings whose game folder and its parent are both gone, since that drive is only unmounted (microSD card, external or network disk) and the library scan re-caches the record once it is back; each strings file records its `gamePath` for this (`removeStringsOwnedBy()`). A record that `checkInstallation()` re-caches from the game folder while this game's strings are gone (another card in the slot) gets its component marked not installed in both copies, so the install dialog offers achievements again. Saving them (`commitAchievementStrings()`) runs after the game files are copied, so a failure only drops the achievements component, never the install.
- Downloads go through the Supabase Edge Function `get-download-url` (invoked by `getSignedDownloadUrl()` in `src/main/tracking.ts`) that enforces rate limits. Writes to `<output>.part`; a `NetworkError` **preserves** the `.part` for resume, 404/cancel deletes it. Pause aborts with reason `'PAUSED'`, persists to `userData/paused-downloads/`, and throws `PausedSignal` at the IPC boundary so the renderer sees `{ success: false, paused: true }`. Resume refreshes the signed URL after 55 minutes.

## Game detection and Steam

`src/main/game-detector/` has eleven modules: `steam`, `gog`, `epic`, `xbox`, `uplay`, `ea`, `rockstar`, plus `heroic`/`lutris`/`egl-linux` (Linux helpers behind GOG and Epic) and `kurin` (a separate catalog source via `syncKurinGames()`, not a path detector). `detectGamePath(installPath, steamAppId?)` switches on the seven store types and returns `exists: false` for `emulator` and `other`. GOG and Epic **do** resolve on Linux via the Heroic and Lutris helpers, and Epic also through the native Epic Games Launcher (EGLv2, `egl-linux.ts`): its append-only `~/.local/share/com.epicgames.eglv2/installations.jsonl` is replayed (last line per `installationId` wins), installs match by folder name, case-insensitively. The log has no titles, so EGLv2 games stay out of «Доступно з Epic». EGL registers no `com.epicgames.launcher://` handler on Linux, but its AppImage takes the link as an argument, running or cold (it then stays in the tray), so `launchEglGame()` (`utils/egl-launcher.ts`) passes it `com.epicgames.launcher://apps/<namespace>%3A<itemId>%3A<artifactId>?action=launch&silent=true` and EGL adds the per-launch Epic auth; the manifest's `AppNameString` does not resolve there. The AppImage path is recorded nowhere: it comes from the running process (comm `EpicGamesLaunch`, argv0) or the usual AppImage folders. Without one LBK runs what EGL itself runs, on the host via `spawnOnHost()` so the game outlives LBK: `<GE-Proton>/proton waitforexitandrun <exe>` from `compat/runtime/<pin-cache.json version>`, with `STEAM_COMPAT_CLIENT_INSTALL_PATH` = that Proton, `STEAM_COMPAT_DATA_PATH` = `compat/compatdata/<artifactId>` (`WINEPREFIX` its `pfx`) and `STEAM_COMPAT_INSTALL_PATH` = the game dir, but no Epic auth, which only DRM-free games accept. No umu and no `STORE=egs` there: protonfixes' EGS defaults install vcrun2022 into EGL's prefix on the first run. A translation's `steam_launch_options_linux` reaches EGLv2 games too: on install `applyEglIntegration()` (`installer/egl-integration.ts`) merges its args, as written, into EGL's own per-game «Additional Command Line Arguments» (`settings/game-settings.json`, keyed by `namespace:itemId:artifactId`, `additionalCommandsEnabled`/`additionalCommands`, which EGL re-reads before every launch, so writing it while EGL runs is fine), and they apply however the game is started; EGL has no per-game environment, so a translation with env assignments is launched from LBK through the Proton fallback even when EGL is there (no Epic auth), the install says so, and that fallback reads the per-game args itself; while EGL has no GE-Proton pinned yet (it never launched a game), the game goes through the EGL link without the env, logged, rather than not at all. An Epic install on Linux that is not EGLv2's (Heroic, Lutris), or on Windows one without its `.item` manifest, gets no args, and the install reports `launchOptionsError` (`launchOptions.eglGameNotFound`) as the Steam path does. On Windows `steam_launch_options_windows` goes to the same EGL setting, which lives in `%LOCALAPPDATA%\EpicGamesLauncher\Saved\Config\WindowsEditor\GameUserSettings.ini` as `<namespace>:<itemId>:<AppName>_AdditionalCommandsEnabled`/`_AdditionalCommands` in every `[<accountId>_Settings]` section (`utils/egl-windows-settings.ts`, app id from the game's `.item` manifest via `getEpicManifestAppId()`, not a DLC's, which shares the folder). EGL reads that file only at start and writes its in-memory copy back on launch, game exit and quit, so it is edited only while `EpicGamesLauncher.exe` is not running (closing its window only hides it to the tray); otherwise the args wait in the `pending-egl-launch-args` store key, survive an LBK restart (`startPendingEglLaunchArgs()`), are written once EGL is gone (polled every 15 s, and before LBK launches an Epic game), and the install says so. An entry whose file has no account section (signed out) stays queued until EGL writes one back; eight failed `tasklist` checks in a row stop the poll, and the entries wait for the next LBK start. The edit touches only those two lines, quoted the way UE writes values its reader would cut, in the file's own encoding (UE switches it to UTF-16LE once a value is not ASCII): the file also holds EGL's rotating login token (`[RememberMe] Data`), and writing back any older copy of it signs the player out. Env assignments cannot reach a Windows game, so the args are written and the install warns.

- Steam resolution is **app-id-first** via `appmanifest_<appid>.acf`; the installdir map is only a fallback (Steam suffixes duplicate installdirs with the app id). Always pass `steamAppId` — omitting it silently degrades to ambiguous folder-name lookup. `getSteamLibraryAppIds()` is async.
- The «Доступно з GOG» / «Доступно з Epic» filters match the store library's **titles** against catalog `name` with `name COLLATE NOCASE IN (...)` — exact, no fuzzy matching. `getCleanTitle()` (`src/main/game-detector/game-titles.ts`) is a hand-written alias table (catalog title → store title variants, looked up in reverse) applied in `gog.ts`, `epic.ts` and `lutris.ts` before the titles cross IPC, so a game whose store title differs (edition suffix, ™) stays invisible under those filters until it gets an entry there — fix it in the table, not with fuzzy matching in the renderer.
- `src/main/steam-watcher.ts` watches `libraryfolders.vdf`, the `steamapps` dirs and `licensecache` with a 2 s debounce (`DEBOUNCE`).
- Steam bridge (`src/main/utils/steam-bridge.ts`): `getSteamBridge()` / `ensureSteamBridge()` hand out a transport that runs only the named ops of `createOps()` (`packages/lbk-bridge-core/src/ops.ts`, shipped to CDP as `STEAM_OPS_SOURCE` in `src/main/utils/steam-bridge-ops.ts`) — never arbitrary eval. The **plugin** transport is used when the LBK Bridge Millennium plugin is connected, otherwise **CDP** (`steam-cef.ts`) against `SharedJSContext` on a discovered port (8080 first; the User-Agent must contain `Valve Steam Client`), picked by its `https://steamloopback.host` origin (`isSharedJsContext()`): its title counts only on that origin, since any web page in Steam's browser can set it. The port opens only if `.cef-enable-remote-debugging` exists in Steam's working directory **and** Steam restarted since. On macOS that directory is `Steam.AppBundle/Steam/Contents/MacOS` (`MACOS_APP_BUNDLE_SUBPATH` in `src/main/utils/cef-flag-file.ts`), not the data root. Millennium on Windows/Linux deletes that file and closes TCP CDP (`detectMillennium().blocksTcpCdp`) — from the second Steam start on: the first session after activation still has the port, because the file is deleted only after steamwebhelper started — so the flag file is left alone there and Millennium v3 gets the plugin instead. The macOS fork adds `--remote-debugging-pipe`, keeps TCP CDP open next to the pipe, and deletes the flag file about 1 s into every wrapper start (verified live on lbk.4); LBK recreates it whenever the plugin connects (`restoreCefFlagFileAfterMillennium()` on `plugin-connection`), so Steam started later from the Dock still has CDP; `blocksTcpCdp` stays `false` there and `runVerify` switches to plugin-only waiting when it sees a pipe with Millennium v3 (`nextVerifyStep()`). Never remove the flag file while Decky Loader is installed (`isDeckyInstalledSync()`): Decky creates it only in its installer. Launch options, workshop, collections, the self-shortcut, artwork and library app ids all go through the bridge and must handle every `SteamBridgeFailure` (`cef-unavailable`, `steam-not-running`, `cef-blocked`, `millennium-plugin-pending`, `millennium-outdated`).
- **Restarting Steam goes through `restartSteamOrchestrated()`** (`src/main/steam-restart.ts`): it never launches Steam after a failed `shutdownSteam()` (elevated Steam, gamescope, timeout, or a failed process listing before the shutdown or the forced kill: `unknown-state`) and runs queued actions in the gap. It refuses to shut Steam down while `RunningAppID` names a Steam game (`getRunningSteamGameId()`: HKCU on Windows; Linux and macOS Steam never write the key to `registry.vdf`, so Linux reads the `reaper SteamLaunch AppId=<id>` process every game runs under and macOS the `SteamGameId=` every game process inherits (`ps -E`); reason `game-running`), and a forced kill takes only `steam.exe` by PID (plus this session's webhelpers by image; `pkill -u <own uid>` on Linux and macOS) — never `taskkill /T`, which would take the game, or LBK started from its Steam shortcut, with it. Concurrent restarts share one run (`p-memoize`, constant `cacheKey`), so nothing reachable from `orchestrate()` may call `restartSteamOrchestrated()` — it would wait on itself; a caller that joins a run started without `verifyBridge` verifies the bridge itself. The restart prompt fires only from the Settings toggle, at most once per bridge fingerprint (`claimSteamRestartPrompt()`); a verified failure persists as `steam-bridge-verdict` and stops all further prompts until «Перевірити ще раз». The bridge is three modules: `utils/steam-bridge.ts` (transports, `getSteamBridge()` / `ensureSteamBridge()`, status), `utils/steam-bridge-verdict.ts` (fingerprint, verdict and prompt store keys) and `utils/steam-bridge-lifecycle.ts` (`verifyBridgeAfterLaunch()`, `startSteamBridge()` and its `appEvents` listeners).
- **LBK Bridge plugins are TypeScript workspace packages** (`pnpm-workspace.yaml` `packages: [packages/*]`), built by `pnpm build:bridge` (part of `prebuild`) into gitignored output and never committed. `packages/lbk-bridge-core` (`@lbk/bridge-core`, a root **devDependency** so electron-vite bundles it into main; keep it out of `dependencies`, `bundled-dependencies.test.ts` checks) holds `contract.ts` (op `{ args, result }` interfaces, `SHARED_STEAM_OPS` / `PLUGIN_ONLY_OPS`, `BRIDGE_VERSION`, `BRIDGE_PLUGIN_NAME`, `BRIDGE_PROTOCOL`, `BRIDGE_WS_PATH`, `BRIDGE_HOSTS`; main and `src/main/steam-bridge-server/` import them straight from `@lbk/bridge-core/contract`, never a local copy), `ops.ts` (`createOps()`, arg validators on ts-belt's `G` guards), `protocol.ts` (zod/mini for bridge.json and the WS frames, and the handshake HMAC; zod/mini never compiles validators, so Steam's CSP does not matter, and `bridge-artifacts.test.ts` fails on any `Function`/`eval` in a bundle; never call `z.config()`: it writes a `globalThis` object that every zod copy in SharedJSContext shares), `achievements.ts` and `bridge.ts` (`createBridge({ host, dataBase, env })`, all state in the closure; `bridge.events` is a plain `EventTarget` that dispatches `change` whenever status, idle, connectedAt or lastError actually changes and `achievements` whenever `achievementApps()` (the apps with strings in the Steam UI hook's last `achievements.json` read) does, never after `disposed`, and the Decky status line reads it through `useSyncExternalStore`, so the artifact sandbox also gets `EventTarget` and `Event`). The ops reach CDP as an esbuild IIFE (`dist/steam-ops.iife.js`) imported with `?raw`; ESLint lets `ops*.ts` import only siblings and `G` from `@mobily/ts-belt` (esbuild keeps a whole ts-belt namespace, `A` alone is ~45 KB; no zod: the whole bundle goes with every CDP call, `steam-bridge-ops.test.ts` has a size budget). The rest of the core is built on the root's libraries, listed with the same pins in its own `package.json` (knip checks the workspace): `p-timeout` with `customTimers: env` for the retry delay and the handshake and op timeouts (so `bridge.test.ts` drives them through `BridgeEnv`'s fake timers), `p-limit(1)` for the request queue and the achievement passes, `p-wait-for` for the Steam UI wait and the `achievements.json` retries (global timers plus `AbortSignal.timeout`/`any`, which is why the artifact sandbox gets `AbortSignal`). ## Platform branches

Use the helpers in `src/main/utils/platform.ts` (`isWindows` / `isLinux` / `isMacOS` / `getPlatform` / `isPortable` / `forCurrentOS`), not bare `process.platform`. `getPlatform()` can return `'unknown'`, which is why `forCurrentOS` uses an `in` check rather than truthiness.

- **Windows**: read the registry through `registry-js` (`enumerateKeysSafe`, plus `getRegistryString()` in `src/main/utils/registry.ts` for one value), never by spawning `reg.exe`: `reg query` stdout comes through the OEM code page, which has no «І», so Cyrillic install paths would not survive it. The native module is built on install (`allowBuilds` in `pnpm-workspace.yaml`) and is a no-op off Windows. Build `dist:win` only on Windows: off Windows the install leaves a host-OS stub `registry.node`, `npmRebuild: false` packs it as is, and the app crashes on start.
- **Linux/Steam Deck**: `src/main/index.ts` appends Chromium switches (`no-sandbox`, `disable-gpu-sandbox`, `enable-gamepad-extensions`, `VaapiVideoDecoder`, `ignore-gpu-blocklist`) and deletes `GTK_IM_MODULE` / `QT_IM_MODULE` in a top-level `if (isLinux())` block that sits **above the bulk of the imports** and long before `app.whenReady()` — moving it later silently breaks Gaming Mode. `runProton({ protonPath, filePath, args })` prefers the bundled `resources/umu/umu-run`; the installer window renders in Game Mode only with gamescope plus `STEAM_MULTIPLE_XWAYLANDS=1` and `PROTON_VERB=waitforexitandrun`. Extraction prefers a system 7z. Started from a Steam shortcut or in Game Mode, LBK inherits the overlay's `LD_PRELOAD`: every child it starts goes through `getCleanEnv()` (`src/main/utils/host-exec.ts`; used by `spawnOnHost`/`execFileOnHost`, 7z, native installers and the Decky installer) — except `runProton()`, which passes the environment through on purpose because umu clears `LD_PRELOAD` itself under gamescope.
- **The Proton prefix is a throwaway**: `~/lbk-proton-prefixes/<sanitized translit installer basename>`, `rmSync`'d ~1 s after the installer exits. A `steamapps/compatdata/<appId>` prefix is reused and kept only when an appmanifest resolves from the *Proton build's* own folder (`findSteamAppId(dirname(protonPath))`) and that compatdata dir already exists — so assume nothing written into the prefix survives.
- **Flatpak sandbox**: on Linux the app may run inside one, so anything launching an external process (Steam, Heroic, Lutris, host `flatpak`) must route through `flatpak-spawn --host`. The helpers live in `src/main/utils/host-exec.ts`: `isFlatpak()`, `execFileOnHost()` (buffered output, timeout) and `spawnOnHost()` (detached and unref'd; `flatpak-spawn` drops the sandbox env, so its `env` is passed as `--env=K=V`), plus `system32()` for Windows tool paths. A bare `spawn('steam', …)` silently fails for every Flatpak/Steam Deck user.
- **macOS**: builds are **per-arch dmg + zip for x64 and arm64 — not a universal binary**. Liquid Glass is gated on Darwin ≥ 25 (macOS 26). Installs must run `resignMacBundles()` (`src/main/installer/mac-codesign.ts`): replacing `Contents/MacOS/*` or `Info.plist` makes the kernel SIGKILL the game, so the bundle is `xattr -cr`'d and ad-hoc signed with `--preserve-metadata=entitlements,flags` and deliberately **not** `--deep`. A signing failure sets `hasInstallError: true` rather than failing the install.
- **Wine prefixes (CrossOver bottles) on macOS** are read-only detection sources plus their own Steam, GOG Galaxy and Epic Games Launcher; every native integration (`getSteamPath()`, Millennium, the CEF/plugin bridge, the native `localconfig.vdf`/grid, `restartSteamOrchestrated()`, achievements) stays native-only. `src/main/wine/`: `prefixes.ts` lists them (CrossOver's bottle dirs from `CX_BOTTLE_PATH`, `CrossOver.conf`'s `BottlePath` and the GUI's `defaults read com.codeweavers.CrossOver BottleDir`, plus the main-only store key `wine-prefixes` of hand-added ones) as a 30 s synchronous snapshot, because the detectors are sync, emits `wine-prefixes-changed` only when the set changes, and fs-watches the bottle dirs; `dos-path.ts` maps paths both ways through the prefix's `dosdevices` links (on-disk spelling, since Steam writes `c:/program files (x86)/steam` lowercased), and membership is always derived from the path through `winePrefixRefOf()` (an ancestor `drive_c` beside `system.reg`), never stored in a record; it answers `null` off macOS, where a Lutris or Proton prefix holds games that go through Proton. Wine code stays in `src/main/wine/` and reaches the generic modules only through one call each: `wine/bottle-steam-roots.ts` reads each bottle's Steam (`user.reg`'s `SteamPath` via `wine-registry.ts`, a port of Wine's own reader that decodes `\\` and `\xNNNN` UTF-16 escapes and parses a file once into a map, `parseRegKeys()`, since a bottle's `system.reg` is megabytes) with the store-agnostic helpers of `game-detector/steam-library.ts`, and keeps its own caches; `steam.ts` stays native-only, and only `getInstalledSteamGames()` merges the bottles' games after the native ones (`invalidateSteamInstalledCaches()` clears theirs too); `detectGamePath()` is native-only, `detectGamePaths()` appends `bottleGameCopies()` (`wine/bottle-game-copies.ts`, one finder per store: Steam, GOG from `system.reg`'s `Software\(Wow6432Node\)GOG.com\Games\<id>` (`bottle-gog.ts`, DLC with `dependsOn` skipped), Epic from EGL's `InstalledItems\*.egi` and older `.item` manifests (`bottle-epic.ts`), each with `GamePath.wine`; `getAllInstalledGamePaths()` adds the GOG and Epic ones through the `bottle-installed` store of `store-cache.ts`, fingerprinted by those files), which the install dialog offers separately (`InstallOptions.winePrefix`, `copyKey()` in `utils/installTarget.ts`), and an install or launch that names a bottle asks `findBottleGameCopy()`; `steam-watcher.ts` adds `readBottleSteamLibraryFolders()`, and `applySteamIntegration()` hands a bottle copy to `installer/bottle-steam-integration.ts`. A copy in a prefix is the Windows build (`resolveGameBuildOs()`), takes the Windows installer (`checkPlatformCompatibility(game, true)` runs after the copy is known), runs it through `wine/run.ts` (CrossOver: `wine --bottle <abs prefix> --no-gui --wait-children <C:\ path>`; it finds a file only by its Windows path; a hand-added prefix: Homebrew/WineHQ `wine` with `WINEPREFIX`), gets its Windows launch options in that bottle Steam's `localconfig.vdf` only while that Steam is closed (`wine/bottle-steam.ts`; Wine replaces argv and the environment `ps` shows, so a running bottle Steam is found by `lsof -c steam.exe -d cwd` inside the prefix, and a failed check counts as running), else queued in `pending-wine-launch-options` and polled every 15 s, its artwork in that Steam's grid through `prefixArtworkTarget()` (records and backups under `steam-artwork/wine/<hash>/`, files only), no achievements, and «Грати» goes through that bottle's store client (`wine/bottle-launch.ts`): `<bottle Steam>/steam.exe -applaunch <id>`, `GalaxyClient.exe /command=runGame /gameId=<id> /path=<C:\ path>` (the game's own `exe` without Galaxy), or EGL's `com.epicgames.launcher://apps/<ns>%3A<item>%3A<artifact>?action=launch` link handed to the handler `system.reg` registers (`url-handler.ts`). Epic launch options are not written into a bottle's EGL; the install says so (`launchOptions.eglInWine`). CrossOver ignores the folder it is spawned in, so `run.ts` passes `--workdir` with the file's own folder (a game launcher that starts its game by a relative path needs it). The Windows build itself under Wine: `isRunningUnderWine()` (`utils/wine.ts`) switches Chromium to in-process SwiftShader ANGLE in `src/main/index.ts` (the GPU process paints black), and `resources/installer.nsh` replaces the NSIS app-running check under Wine (`wine_get_version` in ntdll), where `powershell.exe` is a stub that exits 0 and `findstr` ignores `/B` and `/C:`, so the stock check always sees LBK running.
- **Open http(s) links through `openExternalUrl()`** (`src/main/utils/open-external.ts`), never `shell.openExternal` directly: on Linux it resolves the browser itself (xdg-settings → Flatpak → native binary, cached) because SteamOS's xdg-open hands the URL to the Discover store. It also rejects `file:`/`javascript:`/`data:`/`vbscript:` and returns `{ success, error }` rather than throwing. Bare `shell.openExternal` is reserved for launcher protocol URLs (`epic://`, `uplay://`, `steam://`).

## Renderer

State is split three ways and the split is intentional.

- **Data is managed only by React Query, XState and Zustand; never invent a layer of your own on top of them.** Server state and its writes are React Query (`useQuery`, `useMutation`, pending and failed writes through `useMutationState`, `invalidateQueries` after a write or an event), multi-step flows are XState machines, client state is a Zustand store. No hand-made overlay stores, cache-patch helpers, refetch schedulers, attempt counters or module-level `let` state standing in for what these libraries already do.
- **React Query is only for backend data, and not for all of it.** It holds what the server answers through main (network reads, review pages, writes) and catalog reads keyed by a view's inputs (a game's recommendations, the home page's newest and updated lists per `hideAiTranslations`). Backend data that main mirrors into SQLite and keeps current by push events, such as store discounts (`store_discounts` → the `storeDiscounts` resource), likes and ratings, is a resource (see IPC), never React Query. State of this machine is never React Query either (install records, files LBK writes such as `steam-artwork/<appId>.json`, Steam / Millennium / Decky state, store libraries, detection): what main pushes is a resource (`steamBridgeStatus`, `pluginHostState`), and what one flow reads once comes back from that flow's own IPC call and is passed down (`availablePlatforms` and `steamArtworkApplied` from `useInstallation`'s pre-check into `InstallOptionsDialog`). So is any catalog read that depends on what is on this machine or that every view shares: the `facetRows`, `catalogOptions` (teams and tag options), `libraries` and `installedTranslationIds` resources feed the filters, and `homeInstalled` holds the catalog games installed here and the number of installed game folders, which the home page shows.
- **14 Zustand stores** in `src/renderer/store/`. The five with middleware (`useSettingsStore`, `useSubscriptionsStore`, `useWorkshopInstallsStore`, `usePromoModalStore`, `useEverInstalledStore`) and `useChangelogStore` use the curried `create<Interface>()(...)` form; the plain eight use `create<Interface>((set, get) => ...)`. Colocate actions, and read across stores with `OtherStore.getState()`, never a hook.
- Review writes are React Query mutations: a reply or an edit through `reviewWriteOptions()` (`src/renderer/queries/reviewWrite.ts`, key `['review-writes', gameId]`), the feedback form's post through `feedbackPostOptions()` (`src/renderer/queries/submitFeedbackPost.ts`, key `['feedback-posts']`). Both use `networkMode: 'always'`, since main reports an unreachable server as a failure that a paused mutation would hide; review writes also use `gcTime: Infinity`, so a failed one waits for its resend or discard in whichever tab it was written (memory only, gone on restart). Each entry has one write at most: `createReviewActions` forgets the previous one before it sends (`forgetReviewWrite()`, `src/renderer/queries/entryWrites.ts`), so an edit of a reply that only its answered reply write showed carries that reply as `unlisted` (`unlistedReply()`), shown on pages asked for before the reply's answer, and discarding such an edit refreshes the list. The pages are never patched: `useGameReviews` reads the writes with `useMutationState` (`reviewWriteState()`) and lays them over the cached pages in `withReviewWrites()` (`src/renderer/utils/withReviewWrites.ts`), keeping an answered write on each page asked for before its answer (`fetchedAt < answeredAt`; the query function stamps every page, since `fetchNextPage` moves the query-wide `dataUpdatedAt` too). There a refused reply or a removed entry leaves the view (a root takes its thread; replies under a reply that left show on the first level until the refetch), an `editRejected` answer drops `pendingText` and keeps the text everyone sees, and a failure shows its resend. A `rejected` failure resolves (verdict null: the server stored nothing); every other failure throws `ReviewWriteError` and stays resendable, and `needs-author` forgets the author, opens the picker and resends the same id once. The machine's nickname is the `['review-author']` query (`reviewAuthorQuery`: kept for the session once there is a nickname, asked again on every picker open without one, so the picker starts from the server's spins left, and `networkMode: 'always'` like the writes): `useReviewAuthorStore.ensureAuthor()` reads it through `queryClient.query()` and opens the picker when there is none, every waiting caller sharing one `Promise.withResolvers` in the store, and a claim or `author_required` invalidates it. `onSuccess` shows a refusal's toast (`showToast()`, never in the notification list) and refreshes the game's reviews through `refreshGameReviews()`. Review events reach the renderer through `src/renderer/store/reviewEventsBridge.ts` → `handleReviewEvents()` (`src/renderer/queries/handleReviewEvents.ts`): a reply becomes a `feedback-reply` notification (text `notifications.replyBy`, name by `authorRole`) and refetches unless `addReplyNotification` dropped it as seen, since the event has no avatar seed; a moderation verdict is claimed once per entry and `at` (`claimModerationEvent`), then adds its notice (`addNotification`, a toast only when live) and refetches, unless the viewer's own write or feedback post on that entry is still pending or its answer showed this verdict no earlier than the event's `at` (`isAnswered`, with a minute's leeway for this machine's clock against the server's), so a restore after a removal is still announced. A held edit (`pending`) adds no notice. A batch refreshes each game once through `refreshGameReviews()`, which cancels a first load still running before it invalidates (an invalidate joins a load without data, which would land with what it read before). `FeedbackModal` remounts on every open (`key` in `GamePage`), so an open starts clean while the closing one keeps its content through the exit animation.
- **React Query** also covers the read-only fetches: the catalog queries in `src/renderer/queries/` and the network reads (`useNewsFeed`, GamePage's `['game-banners', id, slug]`). **Any hook reading the local SQLite catalog must go through `useSyncAwareQuery`** (`src/renderer/queries/useSyncAwareQuery.ts`), which forces `enabled: syncStatus === 'ready' || 'error'`. Skipping it caches an empty result for the 5-minute default `staleTime` during the Supabase sync. Non-React-Query hooks hand-roll the same guard (`useDeepLink.ts` waits on `useStore.subscribe`). Catalog-derived queries go stale through IPC push events: their owner subscribes and calls `queryClient.invalidateQueries` after a 300 ms debounce. `useFacetData` reads the filters' resources, subscribed on idle; main re-reads them on `catalog-changed` (every catalog write after the startup sync emits it: realtime upserts, deletions, visibility, test games), `library-changed`, `installs-changed` and Workshop changes, while a filters open only re-checks the store libraries; every pushed value is a new object, whose identity `useFacetCounts` watches. A rename or keyword edit leaves the rows equal, so `useFacetCounts` also refetches the search matches 300 ms after `game-updated` / `game-removed` while a query is typed. A first read that failed ends a loader as `useResource(key).status === 'failed'`: the home sections hide, the filters' teams and tags come out empty. Banners use `staleTime: Infinity` and a short 5-minute `gcTime` because the server caps impressions per `machine_id`, so a later visit asks again.
- **A catalog list that push events keep current is a resource, not React Query.** Main reads it once the catalog is ready (`afterCatalogSync`, standing in for `useSyncAwareQuery`) and again on every event that changes it, and components read it with `useResource(key)`. `ratings` is the shape: both rating lists, re-read on `counters-changed`, `catalog-changed` and the AI-filter toggle (`hide-ai-changed`); a failed read keeps the last list, and `RatingsPage` shows its failure as `useResource('ratings').status === 'failed'`. Such a list is never paged over the port: main returns it whole, and a long one renders through `@tanstack/react-virtual` (`GameList`, `HorizontalGameList`) or is paged in the renderer (`RatingsTable`: 10 rows a page through `Pagination`, the search over the whole list). React Query stays for what has a cache life of its own: network reads, writes, and catalog reads keyed by a view's inputs.
- Review notices (toast, notification center, tray via `show-system-notification` → `navigate-to-game` with a `GameLinkTarget`, which `sendToReadyPage()` in `src/main/window.ts` holds until the page's `renderer-ready` when the click recreated or reloaded the window) open `/game/:id?tab=reviews&thread=<feedbackId>&entry=<entryId>` from `gameLink()` (`src/renderer/utils/gameLink.ts`), or `/game/:id` without the ids; `SystemNotificationAPI` in `src/shared/game-link-target.ts` types that IPC and merges into `window.d.ts`'s `WindowControlsAPI`. `useGameTabFromUrl` reads the link with `readReviewLink()` (no zod in the renderer: the ids come only from `gameLink()`, built from server ids) and picks the tab; `useGameReviews` puts the link's thread and the type filter in the query key (`[...gameReviewsQueryKey(gameId), threadId, type]`, the thread read off the link on its first render and kept while the tab is mounted, dropped under a type filter, and a link resets the filter to all) and sends the thread as `focusId` with page 0 only; a type filter is sent as `type` and narrows the page, cursor and `total` (the viewer's threads, for paging only; nothing shows it as a count), and a filter switch shows the loader while its first page loads; main puts the `focus` thread first in `items` (`with-focus.ts`), and `GameReviewsTab` dedupes it (`A.uniqBy`). The link waits for that list to settle (data, `fetchStatus` idle, since a refetch paused offline is not fetching): events and write answers refresh every list of the game, so a cached one already holds what a notice links to. Then `useReviewFocus` scrolls and the tab clears the URL with `replace`, or the link ends without a scroll when the thread is missing, with the `gameReviews.focusMissing` note, or `gameReviews.focusFailed` while the list's last refetch failed; it keeps the last link's note after the URL clears and hides it while another link loads. `loadNextPage()` passes `cancelRefetch: false`, since a next page would cancel the refetch that brings a write's answer; a call during that refetch joins it and adds no page, so the sentinel (`useInfiniteScrollSentinel`'s `isBusy`) waits while anything fetches and looks again after. The reveal (`revealEntry()`, `src/renderer/utils/revealEntry.ts`) centres the entry and lights it (framer's `animate()` on its tint, 1 s, held still with animations off) once the scroll's promise settles (Chromium 152's `scrollIntoView` returns `Promise<ScrollResult>`, typed in `src/scroll-into-view.d.ts` because lib.dom still says `void`), leaves it unlit when that scroll was interrupted (a newer reveal, the player's own scroll), and gives the gamepad to the entry's first action through `selectEntryAction()` (area `main-content`, then `selectGamepadTarget()`, the half of `moveFocusTo` without its scroll: a text field is only marked `data-gamepad-selected`). While a dialog is up by the loop's own check (`getTopDialog()`, which also sees a closed dialog playing its exit, as `NotificationModal`'s after a click), it selects nothing, since an action behind the backdrop would take the dialog's presses, and leaves the entry's element id in `useGamepadModeStore`'s `entryHandOver`; the loop's modal close takes it (`takeEntryHandOver()`) and selects that entry in place of the opener, a newer reveal replaces it, leaving gamepad mode drops it, and every other close restores the opener as it always did; the loop keeps one opener per stacked dialog (`nextDialogFocus()`), so closing a dialog over another gives the gamepad back to what opened it there. `handleMainContent` keeps focus or a mark already inside the area on entering, so the primary action does not take over from the entry.
- `GameTabs` is a compact segmented control of icon-only tabs (the label is `sr-only` and a `Tooltip`), under the hero; it is not sticky. Picking a tab renders it first (`flushSync`, or the scroll would be measured against the old panel's height) and then scrolls its panel to the top of the game page's scroll container (`useTabPanelScroll()`); a link with only `?tab=reviews` does the same. Every review count (the tab, the reviews header, the filter chips) comes from the game row alone, through `reviewCounts()` (`src/renderer/utils/reviewCounts.ts`): `games.reviews` is every publicly visible comment, published public roots plus their visible replies (staff and author replies included), `games.error_reviews` the same within `error` threads, so «Усі» is `reviews`, «Відгуки» `reviews − error_reviews` and «Помилки» `error_reviews`; they stay live through the counters feed with no extra request, and a hidden game shows 0, since the server lists none of its public threads. The list response carries no counts. The reviews tab shows a dot while the game has unread review notices (`isGameReviewNotice()`: `feedback-reply`, `review-published`); the mounted reviews tab marks them read (`markGameReviewNoticesAsRead()`). A `review-rejected` notice stays unread, since the removed entry is gone from the tab and only the notice says why.
- Deep links (`lbk://games/{slug}/{team}`, parsed by `parseDeepLink()` in `src/main/deep-link.ts`; `?tab=reviews` sets `DeepLinkTarget.openReviews`, which the landing's reviews section uses to open the reviews tab) resolve in main through `find-deep-link-game-id` (`src/main/db/deep-link-game.ts`: one `VISIBLE_GAMES_SQL` query by slug-or-id, team matched in JS because SQLite's `lower()` folds ASCII only); never load the whole catalog in the renderer to look one game up.
- `src/renderer/hooks/useGames.ts` is **not** React Query — it is hand-rolled `useState` + `AbortController` + four IPC listeners (`onGameUpdated`, `onGameRemoved`, `onInstalledGamesChanged`, `onSteamLibraryChanged`) that patch the list in place. Status and author filters run in SQL; content-type filters (`with-achievements`, `with-voice`, `from-workshop`) are AND-combined client-side. A new filter type needs both the SQL path **and** `matchesContentTypes`, or realtime rows bypass it. It does no debouncing of its own and fires an IPC/SQLite query per prop change — the 300 ms debounce lives in its single caller (`useDebounce(searchQuery, 300)` in `Sidebar.tsx`), so a second search entry point wired straight to `useStore.searchQuery` would run an FTS5 query per keystroke.
- **Millennium / Decky setup UI** is one modal, `components/Modal/SteamPluginSetup/SteamPluginSetupModal.tsx`, opened only through `useSteamPluginSetupStore.openSetup(variant, source)` and mounted in `MainLayout` after `GlobalModal` (so it stacks on top; the install-success action closes the global modal rather than `keepOpen`). Every `Modal` closes on Escape only while it is the top dialog (`getTopDialog()`), and `SetupFrame` also captures Escape at `window`, so the dialog underneath does not close with it. Each flow is an xstate machine next to it (`millenniumInstallMachine.ts`, `millenniumUninstallMachine.ts`, `deckySetupMachine.ts`) run with `useMachine(machine.provide(…))`: the machine files touch `window.electronAPI` only inside their default actors, so node tests import them and swap the actors, and the flow component provides the actors that drive a `useActionPhase` button (its `run()` wraps the IPC call). The flow sends the plugin-host state in as `HOST_STATE` (the Decky machine is also seeded with the stored state through `input`, so its `always` guards see it on the first render); the Decky flow finishes on that pushed state (main's Decky watcher), never on a poll. Steps are view builders in `SteamPluginSetup/steps/` (`millenniumIntroView()`, `restartChoiceView()`, `resultView()`, …) that return a `SetupView` (title, dismissable, body, footer), and each flow renders exactly one `<SetupFrame view={…}>` — a step that rendered its own frame would remount the `Modal` and replay its open animation on every transition. Millennium copy and decisions (`failureStep()`, `introMode()`, `isPluginConnected()`, `RestartChoice`) live in `millenniumSetup.ts`. Offers are contextual only — the install-options note + badge, the install-success modal, Settings — never at startup, and only while `steamCefDebuggingEnabled` is on; all four read one model, `utils/pluginHostOffer.ts` (`millenniumOffer()`, `deckyOffer()`, `deliveryNote()`, `successOffer()`, `offerAction(name)` with its label from `pluginOffer.<name>`), and open targets through `openOfferTarget()`; the Settings rows are `pluginHostEntries()`. In `InstallOptionsDialog` the achievements checkbox (`InstallOptions/AchievementsOption.tsx`) is locked until the badge is ready (`millennium`, `decky`, `after-restart`; `achievementsOptionState()` in `utils/installOptions.ts`), with the install button right under it; it unlocks by itself when main publishes a new `steamBridgeStatus`. The achievements badge (`ui/AchievementsDeliveryBadge.tsx`) only renders `SteamBridgeStatus.achievements`. Both feed `useEverInstalledStore` (likes and reviews stay open after a translation is removed) through `initEverInstalled()` (`store/everInstalledBridge.ts`, called in `main.tsx`), one persist write per change of either store.
- Persistence goes through electron-store, never `localStorage` (an ESLint **error** via `no-restricted-globals`). The one exception is the one-time `localStorage` → electron-store migration that runs at module import time in `src/renderer/store/electronStorage.ts` (keys `lbk-settings`, `subscriptions-storage`, `has-launched-before`, guarded by `__migration-v1-done`) — the tree's only `no-restricted-globals` disable; do not "clean it up", it must keep running before any store's `getItem` or every pre-migration user silently loses settings and subscriptions on upgrade. `electronStorage.ts` `getItem` is deliberately synchronous (`sendSync`) so rehydration has no flash of defaults. `useSubscriptionsStore` keeps the newest 200 `notifications` (recounting `unreadCount` after the trim), 500 `seenFeedbackReplyIds` (reply entry ids, the same ids the replaced replies stream stored, so an upgrade never notifies an old reply again) and 500 `seenModerationEvents` (`reviewModerationKey()`: the entry and the verdict's `at`; not `editedAt`, which a rejected edit leaves as it was); the lists have to cover every live event since the last catch-up (live events never move the watermark) plus its 5 s overlap. Manual memoization stays in the two lists and the rows they render, in `useActionPhase` (shared byte for byte with lbk-admin and lbk-landing), on a function an effect depends on (`exhaustive-deps` asks for it, and a skipped compile would otherwise loop), and wherever removing it widens a scope.

## Conventions

- **Named exports.** Components are function declarations, `export function Name(props: NameProps)`, with a local non-exported `interface NameProps`. `memo` wraps a named function, `export const Name = memo(function Name(props: NameProps) { … })`, so DevTools keeps the name. `React.FC` is banned (`@typescript-eslint/no-restricted-types`), and so is the default `React` import (`no-restricted-imports`), since the JSX runtime is automatic: import `memo`, `Fragment` and hooks by name, and write React types through the global namespace (`React.ReactNode`, `React.MouseEvent`), because a named import of an event type would shadow the DOM one. The only default exports in the tree are `src/renderer/components/MainContent/Gallery.tsx` and the three plugin entries their toolchains require (`packages/lbk-bridge-decky/src/index.tsx`, `packages/lbk-bridge-millennium/frontend/index.tsx`, `packages/lbk-bridge-millennium/webkit/index.tsx` — ttc's webkit wrapper calls only the default export, so a named one still builds and does nothing in Steam). No re-exports and no barrel files: import every symbol from the module that defines it (`@/main/game-detector/store-cache`, `shared/types`, …), and remember knip fails the build on an export nobody imports.
- Hooks and stores: one `use*` export per file, file named after the export.
- **One component per file; split by responsibility as you write.** A `.tsx` file declares one component. A sub-component, hook or helper with a job of its own goes into its own file beside it, named after its export, even when only that one file uses it. Several declarations share a file only when they are small private parts of the one thing it exports: a guard, a formatter, a local type. The same holds outside React: a module that has grown a second responsibility is split, and a helper that a second file needs moves to a shared module instead of being copied. `max-lines` (400) is the ceiling, not the signal to split.
- `import type` for type-only imports (`consistent-type-imports`, a warn). In `src/shared/types.ts` and `src/preload/index.ts` the `import type` of `BannerData` / `GameBannersResult` / `ImpressionType` from `@/main/db/banners-api` is load-bearing rather than stylistic: that module value-imports `getSupabaseClient`, so downgrading it to a value import drags the main-process Supabase client into the renderer and preload bundles.
- No `any` (ESLint error). No `var`, no duplicate imports (both errors).
- Escape hatches are `/* eslint-disable rule -- reason */` with the reason after `--`. There are zero `@ts-ignore`, `@ts-expect-error` and `biome-ignore` in `src`; keep it that way.
- ESLint warns past 400 lines in a file (`max-lines`, blank lines and comments not counted; off for the generated `database.types.ts`). Split a growing module by responsibility rather than letting it pass that, and keep new files under it. The files over it were already over 400 on main; `src/shared/types.ts` dropped under it once its Steam-bridge and plugin-host methods moved to `SteamPluginHostAPI` and the reviews methods to `GameReviewsAPI` (installer and updater ones are `InstallerAPI` and `UpdaterAPI`, the resources port `ResourcesAPI`); a new group of methods gets its own interface the same way.
- Every `if`/`else` uses a block statement — `style/useBlockStatements` is Biome's only enabled lint rule (`preset: none`).
- Formatting: 2-space indent, 90 columns, single quotes, es5 trailing commas, always semicolons.
- Console logs carry a bracketed module tag: `[Main]`, `[Installer]`, `[Database]`, `[Migrations]`, `[SyncManager]`, `[Steam]`, `[Downloader]`, `[Proton]`, `[App]`, `[Store]`, `[useGames]`, `[Analytics]`. `console.error` in main is also captured as a Sentry event (`captureConsoleIntegration`), because `src/main/index.ts` calls `initLogger()` before `Sentry.init`: Sentry then wraps the logger's methods and sees the caller's arguments. Called after it, `initLogger()` would replace Sentry's hook and every main-process error would stay out of Sentry.
- Prefer an existing dependency over a hand-rolled helper — check `package.json` (and npm) before writing one. What already covers the usual cases:
  - `@mobily/ts-belt` is the utility library: `G.isObject` / `G.isString` / `G.isArray` instead of hand-written `isRecord` guards, `F.debounce` / `F.throttle` / `F.makeControlledDebounce` / `F.makeControlledThrottle` / `F.once` / `F.memoize` instead of `setTimeout` bookkeeping, `A` / `D` / `pipe` for collections. `F.throttle` fires the first call at once and drops the rest of the window (no trailing call).
  - ts-belt has no sleep or timeout: `import { setTimeout as sleep } from 'node:timers/promises'`, and `p-timeout` (bundled, ESM-only; `fallback` instead of a rejection) for promises that take no `AbortSignal`. Steam process polling is `waitForSteamStart()` / `waitForSteamGone()` in `steam-process/lifecycle.ts`; `findSteamPids()` reads a 500 ms shared snapshot (`steam-process/snapshot.ts`) for status, host-state and endpoint reads, where a failed listing shows as no Steam; `listSteamPids()` lists afresh for shutdown, kill and apply decisions and returns `null` for a failed listing; `isSteamRunning()` / `isSteamStopped()` and the polls always list afresh, and the first two read a failed listing as Steam running, so no write or skipped shutdown rests on it (`probeSteamRunning()` keeps the `null` for the Steam monitor, which takes it for neither a start nor an exit). Every listing counts only this user's Steam: the real uid in `/proc/<pid>/status` (a `ruid` column of host `ps` in Flatpak), `pgrep -u` / `ps -U` on macOS, LBK's own session on Windows (`SESSION eq` for `tasklist` and `taskkill`, `SessionId` in the CIM query; every session when it cannot be told). All of them are async and there is no sync variant: a sync `tasklist` blocks the main process. CDP port discovery from process arguments and `logs/webhelper.txt` is `utils/steam-cef-discovery.ts` (on Windows it needs PowerShell CIM for command lines; tasklist, behind the snapshot, has none).

Concurrent callers share one run through `p-memoize` with `cache: false` and an explicit `cacheKey`; serial chains are `p-limit(1)`; never add `process.on('SIGINT' | 'SIGTERM')` in main, because any listener disables Node's default exit on that signal (the old Lutris handlers kept LBK alive through logout/shutdown SIGTERM); polls are `p-wait-for` (`timeout.fallback`, `resolveWith`); a child-process wait is `events.once(child, 'close', { signal: AbortSignal.timeout(ms) })`; start guards are `F.once`. The Steam monitor is the xstate machine in `src/main/steam-monitor-machine.ts`, implemented through `.provide()` in `steam-pending-actions/monitor.ts` (`pauseSteamMonitor()` is there too). Tests reset this state through the module's reset function (`resetMillenniumDetectCache()`, `resetHostFacts()`, …), `appEvents.off()` or `vi.resetModules()`.
  - Shared helpers, one home each: `errorMessage()` / `errnoCode()` (`src/shared/errors.ts`) instead of `instanceof Error` ternaries and `as NodeJS.ErrnoException` casts; `sha256()` / `sha256File()` / `sha256FileSync()` (`src/main/utils/hash.ts`); `readFileOrNull()`, `readTextOrNull()`, `readlinkOrNull()`, `realpathOrNull()`, `isPathInside()`, `isSameFile()`, `missingFiles()`, `pruneDir()` (`src/main/utils/fs-safe.ts`); `copyFileAtomic()` / `replaceDirAtomic()` next to `writeFileAtomic()`; `sendToRenderer()` (`src/main/window.ts`) for main → renderer pushes. ## Comments

Everyone here reads TS faster than prose about TS. **Default to no comment** — write one only for what the code can't say: a workaround and what breaks without it, a business or regulatory rule, a non-obvious ordering or idempotency constraint.

Never narrate a function body — no step-by-step, no `// Step 1:`, no `// loop over users` above a loop. No JSDoc restating the signature; types carry it. No divider or changelog comments, no commented-out code. TODOs need an issue number.

Comments that do exist stay to **one line**; never write a multi-line comment block.

**Comments are always written in English**, regardless of surrounding Ukrainian UI copy — this applies to `//` and `/* */` comments, JSDoc, and `eslint-disable` reasons alike. This is unrelated to the UI-copy rule above: user-facing Ukrainian strings (JSX text, store copy, error messages shown to the user) stay Ukrainian as always; only comments must be English.

- **E2E selects on visible text read by key and on ARIA**, e.g. `getByPlaceholder(t('gameSearch.placeholder'))`, `getByText(t('filterBar.filters'))`, `` `button[title="${t('sidebarNav.settings')}"]` ``, `getByRole('dialog', { name: t('settings.title') })`, `.drag-region`, `[data-nav-group="game-list"]`. There is not one `data-testid` in `src` or `e2e/tests`. Rewording a message is safe; renaming its key, dropping the settings gear's `title`, or `Modal.tsx`'s `aria-labelledby` (a `useId` per dialog, so stacked dialogs keep their own names) breaks e2e, which runs on every PR (`e2e.yml` also calls `ci.yml`).
- `test/games.json` is a **dev-only hot-reload catalog override** watched by `games-repository.ts`, not a vitest fixture.
- `pnpm type-check` does not cover `e2e/` (own tsconfig, never invoked) and does not cover `electron.vite.config.ts`: `tsconfig.json` includes only `src`, and the referenced `tsconfig.node.json` lists `vite.config.ts` (which does not exist) and `vitest.config.ts` — and project references are not built by a bare `tsc --noEmit`. Verify before relying on either being checked.

## Build, release, secrets

- `resources/extensions/spellfix.{dylib,so,dll}` is compiled by `scripts/build-spellfix.js` from `resources/extensions/spellfix.c`, is gitignored (`resources/extensions/*` with a `!*.c` negation), and is a hard `extraResources` requirement — `pnpm dist:*` without a prior prebuild has nothing to copy. `pnpm build` only triggers it because `pnpm-workspace.yaml` sets `enablePrePostScripts: true`. Windows needs MSVC (`cl.exe` located via vswhere). `isUpToDate()` compares mtimes only (on macOS it also rebuilds a dylib that `lipo -archs` shows is not universal, since one `spellfix.dylib` goes into both the x64 and the arm64 build), so a stale binary survives a better-sqlite3 upgrade — delete it by hand after upgrading.
- At runtime a missing spellfix degrades gracefully: search just loses typo tolerance.
- `VITE_*` values are inlined by Vite **into the main process too** (`src/main/db/supabase-credentials.ts`, `src/main/game-detector/kurin.ts`, `src/main/index.ts`, `src/main/turnstile/page-url.ts`). Rotating the Supabase anon key silently breaks every already-shipped binary until a rebuild and release. `.env.example` lists the keys; `.env` is gitignored.
- Every platform `files` in `electron-builder.config.cjs` is the full `appFiles()` list (`out/**/*` plus exclusions). A platform `files` replaces the root list as the app matcher, and a list of exclusions alone makes electron-builder add `**/*` and pack the whole repo (`.env`, `src/`, earlier `release/` builds) into `app.asar`.
- `verifyUpdateCodeSignature: false` in `electron-builder.config.cjs` is deliberate (Azure Trusted Signing's root ships via a Windows Update many users lack). Do not "fix" it. Windows signing only activates when `AZURE_TENANT_ID` is set, so local `dist:win` is unsigned by design.
- Two update paths: electron-updater, and a portable-only `latest.yml` poller (`src/main/portable-updater.ts`) that emits the same `update-available` event with an extra `downloadUrl`.
- `LBK_E2E=1` or `--e2e` sets `remote-debugging-port=19222` and disables Sentry and all tracking. The port is a bare literal in three places — `src/main/index.ts`, `e2e/helpers/launch.ts`, `e2e/tests/clear-cache.spec.ts` — change all of them.
- Release is tag-driven (`push: tags: v*.*.*`): draft release → per-OS build with `--publish never` → E2E on the packaged app → `gh release upload --clobber` from `release/<package.json version>`, so a version/tag mismatch uploads nothing. Linux targets are AppImage + rpm; the AUR job downloads `LBK-Launcher-linux.AppImage` by name.

## Do not

- Do not write user-visible text as a literal — not in JSX, main-process messages, notifications, errors or tray menus. Add the key to `uk.ts`, `en.ts` and `be.ts` in `packages/lbk-i18n/src/` and call `t('…')`, even for one word. Tests and e2e read it by key too.
- Do not add a `games` column without all five edits — `pnpm type-check` catches only two of them.
- Do not write a games-listing query without `VISIBLE_GAMES_SQL`.
- Do not put a read or a search on the DB worker — it handles writes only.
- Do not assume a migration ran on a fresh install; it runs on the second launch.
- Do not call `window.electronAPI.checkForUpdates()` — `check-for-updates` has no main handler. `ipcMain.on('windows: restore')` in `window-controls.ts` has a typo'd name no preload code invokes.
- Do not use `localStorage` in LBK's renderer, or `React.lazy` (used nowhere — the cold-start strategy is `isOpen`-gated modals, `useIdleEffect`, `ShaderWarmup`, and deferred image decode).
- Do not edit `localconfig.vdf` while Steam is running, and do not replace the atomic tmp+rename write.
- Do not skip `resignMacBundles()` on macOS installs.
- Do not move the Linux Chromium switches lower in `src/main/index.ts`.
- Do not rewrite or trim `src/shared/changelog.json` — it is append-only. Add the entry for version N **before** tag `vN` is cut: `src/main/changelog.ts` fetches the file as it existed at that tag, so a later commit is invisible forever. It currently holds 2.22.0, 2.23.0 and 2.24.0 (2.23.1 has no entry), so the practical history starts at 2.22.0. `changelog.ts` returns `undefined` on a failed fetch, so its `lru-cache` stores nothing and the next `update-available` (every 30 min) retries.
- Do not edit files not covered by tooling and assume CI caught it: Biome sees only `src/**` (minus `src/lib/database.types.ts`), `packages/**` plus `electron.vite.config.ts`, `vitest.config.ts`, `package.json` and `tsconfig*.json` (`e2e/` and `scripts/` are unformatted), and ESLint ignores every `*.js`/`*.cjs`/`*.mjs` (so `rollup.config.js` and `build.mjs` in `packages/` are unlinted).
